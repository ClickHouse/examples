# Verification suites

Run Bun and dependency commands inside the isolated OrbStack development VM,
following [the maintainer environment](../docs/maintainer-environment.md).

```sh
bun run typecheck
bun run test:unit
```

Unit tests check configuration, authentication, body limits (including streamed
bodies with a dishonest Content-Length), validation, and sanitized errors. They
need no database and deliberately fail if rejected HTTP input reaches a query.

## Managed Postgres integration

Use a disposable, migrated database created through the [README](../README.md).
The runtime connection must use `stock_reservation_app`. Fixture administration
must use a separate account that can insert/delete fixtures and alter the
reservations table, such as the service administrator. Do not point the suite at
a shared production database. Run only one copy against a database at a time.

Store these variables in a private VM environment file; never commit it:

```dotenv
DATABASE_URL=postgresql://stock_reservation_app:PASSWORD@HOST:5432/postgres
TEST_ADMIN_DATABASE_URL=postgresql://ADMIN:PASSWORD@HOST:5432/postgres
PG_CA_CERT_PATH=/absolute/path/to/instance-ca.pem
```

Both URLs must be plain PostgreSQL URLs without query parameters. Both pools use
the application factory's strict certificate validation. The test clients and
tokens are generated by the suite; it does not use your configured API tokens.

```sh
bun --env-file=.deployment/test.env run test:integration
```

Missing database variables fail explicitly rather than silently skipping checks.
The suite exercises two app instances with independent connection pools:

- 32 buyers compete for 9 units; exactly 9 reservations commit.
- 24 simultaneous retries commit one reservation and replay its original body.
- Conflicting payloads, client-scoped keys, ownership, and repeated release.
- A rejected reservation leaves its key available for a later successful retry.
- Real INSERT failure after the inventory decrement rolls back both stock and key.
- A failed release status update rolls back its stock increment and leaves the reservation active.
- Runtime role privileges, encrypted connections, wrong-CA and wrong-hostname rejection.

The creation rollback test installs [a temporary check constraint](fixtures/rollback-guard.sql)
which rejects only generated `test-rollback-` SKUs, then removes it in `finally`
using [the explicit cleanup SQL](fixtures/remove-rollback-guard.sql). The release
rollback test similarly installs [a status constraint](fixtures/release-rollback-guard.sql)
for `test-release-rollback-` SKUs and [removes it](fixtures/remove-release-rollback-guard.sql)
after checking the unchanged stock and reservation. If the process is forcibly
killed during either test, inspect its constraint before manually running the
corresponding cleanup SQL; the next run will fail safely if it still exists.

Fixture SKUs and authenticated client IDs contain a unique run suffix. Cleanup
deletes only those clients' idempotency records/reservations and the exact SKUs
created by the suite. It does not reset seed stock or truncate tables. A crashed
process may leave its generated fixture rows; dispose of the test database after
verification using the README cleanup steps.

The TLS suite also requires the `openssl` command in the VM. The certificate in
`fixtures/untrusted-ca.pem` is an unrelated, public test-only
certificate. Its private key is not included. The TLS suite establishes a valid
connection first, then exercises incorrect trust and a numeric-address hostname
against the same live endpoint. The untrusted CA must fail with a certificate
verification error code. For hostname verification, OpenSSL first connects to
the exact numeric peer address and verifies the genuine DNS identity and CA;
then Bun must reject that address as the expected certificate identity, even
with an ambient `PGSSLMODE=verify-ca`. Bun 1.4.2 may emit only an empty Error with
`errno: 0` for this rejection, so the test permits that specific opaque result
alongside explicit hostname errors. The independent verified-TLS control and
successful application query before/after bound that evidence; generic timeout,
DNS, authentication, and connection-closed errors do not pass. Record actual
runtime and managed-service results in [verification](../docs/verification.md).
